# AppTrust/Unified Policy Artifacts Documentation

## How to Bring Your Own Rego

This repository contains artifacts, scripts, and examples for implementing "Bring Your Own Policy" using Rego within the JFrog AppTrust platform. Follow the workflow below to configure your environment, develop policies, test locally, and deploy rules.

## Environment Setup

Before running any scripts, you must configure your local environment to handle authentication and secrets.

*   **Repository Updates:** Ensure you pull the latest updates from this repository to access all current artifacts and scripts.
*   **The `.env_apptrust` File:** The scripts provided in this repository are configured to retrieve secrets from a file named `~/.env_apptrust`. To set this up:
    1. Make a copy of the `home_dot.env_apptrust` file provided in the repository.
    2. Rename the copied file to `.env_apptrust` and place it in your home directory (`~/.env_apptrust`).
    3. Update the values in the `.env_apptrust` file with the necessary secrets and environment variables for your setup.
    4. Ensure the scripts are updated to reference the `.env_apptrust` file in your home directory.
    *   You must create this file and populate it with the necessary secrets/environment variables.
    *   If you prefer a different method for secret management, you will need to manually modify the Python scripts.

## Understanding Evidence

To write effective policies, you must understand the structure of the JSON evidence generated by JFrog.

*   **Data Structure:** The input data typically contains three main connections: `evidenceConnection`, `artifactsConnection`, and `fromBuilds`.
*   **The Predicate:** The core logic of your policy will rely on the `predicate`.
    *   **Important Nesting Detail:** Currently, the predicate is passed as the full schema. This results in a nested JSON structure where the data is located at `predicate.predicate`.
    *   **Arbitrary JSON:** The content inside the predicate is arbitrary JSON. While JFrog provides the signature wrapper, you must navigate the specific JSON structure inside the predicate to find the data you need.
*   **Retrieving Sample Data:** To view the exact payload structure for your Rego input, export the evidence from an application in JFrog. This will provide the specific `artifactsConnection` or `fromBuilds` evidence needed for accurate testing.

## Developing Rego Policies

When writing custom `.rego` files for the platform, adhere to the following strict guidelines and restrictions:

*   **Package Name:** You must declare the package as `package curation_policies`.
*   **Input Paths:**
    *   Artifact evidence is found in `input.data.artifactsConnection`.
    *   Build evidence is found in `input.data.fromBuilds`.
*   **Required Return Values:** The policy must return two specific values:
    As dictionary in the variable `allow`:
    1.  `should_allow` (Boolean): Determines if the policy passes (`true`) or fails (`false`).
    2.  `explanation` (String): A description of the result.

    ```json
    allow := {
        "should_allow": passed_tests_sufficient,
        "explanation": concat(" ",["Required tests: ", input.params.tests_required])
    }```
*   **Function Restrictions:**
    *   **No HTTP Requests:** External calls (HTTP requests) are strictly prohibited for security reasons.
    *   **String Formatting:** The `sprintf` function is **not** supported. Use `concat` for string concatenation.
*   **Type Conversion:** To convert a number to a string, you must use the function `format_int`.
    *   *Warning:* Some platform documentation may list an incorrect function; `format_int` is the correct function to use.
*   **Best Practice:** Do not hardcode validation thresholds (e.g., "pass 2 tests") inside the Rego. Use **parameters** so the same Rego template can be reused with different rules for different environments (e.g., Dev vs. Prod).

## Local Testing

Use the examples in the `test` directory in this repository to build your own validation of policies locally before deployment.

1.  **Prepare Test Data:**
    *   **Attestation JSON:** Use a full attestation example (e.g., `attestation.json` found in the repo) that replicates the `artifactsConnection` payload.
    *   **Params File:** If your policy uses parameters, populate a `params` file (examples provided in the `test` directory).
2.  **Run the Test Script:**
    *   Use the `rego_test` script provided in the repository.
    *   This script uses `opa eval` to simulate the policy engine behavior.
3.  **Verify Results:**
    *   A successful test will return `true` or `false` along with the `explanation` string.
    *   If the output is a blank dictionary, the Rego is likely malformed or returning a blank statement.

## Deployment (Templates & Rules)

Once your Rego logic is verified locally, use the provided Python scripts to deploy it to the platform.

### 1. Create the Template JSON
Create a template JSON file following the examples in the repo (e.g., `in_total_template.json`). You must add a placeholder in the JSON where the Rego code will be inserted.

```
templates/
├── in_total_template.json
├── out_total_template.json
├── example_template.json
```

### 2. Generate the Template
Run the `createtemplate.py` script.
*   **Function:** This script takes your Rego file and JSON template, converts the Rego into a single-line string (required format), and connects to the platform to create the template.
*   *Validation:* The system will bounce back any Rego containing unsupported functions during this upload process.

### 3. Retrieve Template ID
Run the `get_template.sh` script to list available templates. The script dumps the output into `/tmp/templates.json` Locate your new template and copy its **Template ID**.

### 4. Create the Rule
Create a rule using the **Template ID** generated in the previous step.
*   The **Rule** defines the specific parameters (e.g., `test_count = 2`) for that implementation.

The script, `create_rule.sh`, is used to create a new rule.

Run the script with the desired rule name as an argument:
./create_rule.sh <rule_file_name>

Example:

```bash./create_rule.sh my_new_rule.json```


### 5. Apply to Life Stage
Once the rule is created, navigate to the UI and apply it to specific life stages (e.g., "Entry into Staging").
